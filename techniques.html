Relationship Types
Alternative Approaches
Techniques in the same category and pipeline stage that solve similar problems in different ways. These are interchangeable options — you might choose one over another based on your specific constraints or preferences.
Complementary Techniques
Techniques from different categories but the same pipeline stage. These work well together in combination — using multiple complementary techniques can enhance overall performance by addressing different aspects of the same stage.
Pipeline Chain
Techniques from different pipeline stages that naturally connect in sequence. These represent potential next steps in your RAG pipeline — the output of the current technique can feed into these downstream techniques.
Pipeline Stages
Pre-Retrieval
Techniques that prepare or transform the query before searching the knowledge base. Includes query expansion, rewriting, and routing decisions.
Retrieval Core
The main search and retrieval operations. Includes embedding-based search, keyword search, hybrid approaches, and multimodal retrieval.
Post-Retrieval
Processing and refinement of retrieved results before generation. Includes reranking, filtering, compression, and context optimization.
Generation Layer
Techniques applied during or after the LLM generates a response. Includes verification, self-correction, citation, and reasoning enhancement.
Cross-Session
Techniques that persist or leverage information across multiple interactions. Includes memory systems and feedback loops.
Score Guide
All scores are 1–5.
Note: These criterias scoring is done on estimation only to get an idea of performance.
Performance Boost
How much this technique improves answer quality, recall, precision, or reduces hallucination, based on published benchmarks and production evidence.
5 — Transformative, documented quality gain. A non-negotiable baseline in serious production pipelines.
4 — Clear improvement in most use cases with strong supporting evidence.
3 — Noticeable improvement in specific scenarios. Mixed results across corpus and query types.
2 — Minor or situational benefit. Narrow applicability or only demonstrated on the paper's own dataset.
1 — No meaningful output quality improvement. Serves architectural or compliance goals instead.
Integration Simplicity
How much engineering effort adding this technique requires, based on framework support and infrastructure needed.
5 — A prompt change or single config flag.
4 — One library import or named framework component.
3 — Requires pipeline changes or custom code.
2 — Needs new infrastructure or custom training.
1 — Requires novel model training or research-level implementation.
Latency
How much end-to-end query latency this technique adds. Higher score means less latency added.
5 — Adds no latency or actively reduces it.
4 — Negligible overhead. Imperceptible to end users.
3 — Extra inference call. Tolerable for most applications.
2 — Multiple sequential calls. Noticeable to users.
1 — Severe overhead from multi-step reasoning loops or multi-agent coordination.
Cost
Total additional cost per query including API calls, compute, storage, and amortized training or indexing costs.
5 — Zero or negligible additional cost. No extra API calls, CPU-only computation.
4 — Minimal overhead. One-time index build cost that amortizes to near-zero across queries.
3 — Moderate.
2 — Significant.
1 — Expensive.
Popularity
How widely the technique is actually deployed in production, based on six signals: framework support, GitHub stars, academic citations, coverage in production guides, enterprise vendor adoption, and community discussion volume.
5 — In every major framework with enterprise vendor support. A baseline expectation, not an advanced option.
4 — Named component in a major framework, strong GitHub traction, or featured in multiple independent production guides.
3 — Covered in RAG surveys with growing community adoption. Not yet a default but gaining real production traction.
2 — Published paper with modest citations. Used by early adopters only. No major vendor has productized it.
1 — Research paper only. No proper evidence of production deployment outside the originating lab.
How to Use This Scorecard
New pipeline: Sort by Integration Simplicity descending. Start with everything scored 4–5.
Optimizing existing pipeline: Sort by Performance Boost descending, filter Latency ≥ 3 and Cost ≥ 3.
Cost-constrained: Filter Cost = 5, then sort by Performance Boost.
Enterprise or regulated use: Prioritize high Popularity scores — these have the most documentation and known failure modes.
Popularity ≠ quality. The most widely used technique is not always the best for your specific corpus and query distribution.
